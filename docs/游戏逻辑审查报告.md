## 二、🔴 Bug 1:短牌「三条 > 顺子」完全失效

### 规则约定
`README.md` 与需求都写明,36 张短牌的两处关键差异是:
- **三条 > 顺子**
- **同花 > 葫芦**

### 实测

```
短牌玩法下:
  三条 K (Kh Kd Kc 2s 3d)     类别=3  [3,13,3,2]
  顺子 T 高 (6h 7d 8c 9s Td)  类别=4  [4,10]

  compare(三条K, 顺子T高) = -1  →  三条更小(错)
```

`同花 > 葫芦` 这条是**对的**,只有 `三条 > 顺子` 失效。

### 根因

`src/core/handEval.js:29`:

```js
// 表按「内部类别 → 对外类别」索引。下标:0高牌 1一对 2两对 3三条 4顺子 5同花 6葫芦 7四条 8同花顺
const SHORT_REMAP = [0, 1, 2, 3, 4, 6, 5, 7, 8];
//                            ↑  ↑  ↑  ↑  ↑
//                          三条 顺子 同花 葫芦
```

只交换了「同花 ↔ 葫芦」那一对,**没有交换「三条(3)↔ 顺子(4)」**。
短牌里三条应该是第 4 档、顺子第 3 档,现在两者都没动。

### 连带影响

1. **`categoryKey()` 输出错**(`handEval.js:174-179`):短牌下同花报成 `full_house`、葫芦报成 `flush`。这个函数是给 AI 提示词用的,所以 **AI 会以为自己拿的是另一种牌型**。
2. **`CATEGORY_NAME_SHORT`(`handEval.js:17`)编码了同一条错误规则** —— 数组里 `[3]='三条', [4]='顺子'`。目前没被使用,但留着会误导。
3. **7 张牌同时有「三条」和「顺子」时判成顺子**。子代理的 fuzz 测试跑了 6000 手,找到 **20 处**类别判定与正确规则不一致,例如:
   ```
   10♣ 9♠ 10♠ 10♦ J♥ K♣ Q♦   → 代码判顺子 [4,13],应为三条
   ```
4. **实际摊牌会输错钱**。子代理构造的摊牌用例:
   ```
   999 + A K(三条) 对上 Q 高顺子 → 引擎把底池 200 判给了顺子
   ```

### 复现
```
node tools/audit_shortdeck.mjs     # 最小复现 + 阶梯核对
node tools/audit_eval.mjs          # 完整 183 项(含 17 项失败,大部分是这个 bug)
```

## 三、🔴 Bug 2:短码全下后,下注轮被提前关闭

### 规则约定
下注轮之所以能结束,是因为**没人还欠钱**。只要还有人没跟平,本轮就必须继续。

### 实测(翻牌圈,3 人)

```
seat1 下注 100              → currentBet=100,actor=seat2,pending=[2,0]
seat2 全下到 130            → currentBet=130,actor=0,  pending=[0]

seat1 已投 100,还欠 30 —— 但本轮没有让他行动!

各家最终投入 = [20, 120, 150]
正确应让 seat1 补到 130
```

`seat1` 只投了 120 就直接摊牌了,少跟的 30 筹码**被免掉**。
同时 `actor` 还错误地指向了已经弃牌的 `seat0`。

### 根因

`src/core/engine.js:505-518`,加注分支:

```js
const isFullRaise = target - wasCurrentBet >= st.lastFullRaise;
if (target > wasCurrentBet) {
  if (isFullRaise) {
    ...
    this._rebuildPending(seat);        // ← 只有「完整加注」才重建行动队列
  } else {
    // 短码全下,加注额不足,不重开下注轮
    st.minRaiseTo = Math.max(st.minRaiseTo, target + st.lastFullRaise);
  }                                   // ← 短码全下没有重建队列
  st.currentBet = Math.max(st.currentBet, target);
}
```

在 `engine.js:530`,行动过的人会从队列里被移除:

```js
st.pending = st.pending.filter((s) => s !== seat);
```

所以 `seat1` 一旦行动过就离开了队列。之后 `seat2` 把注额从 100 抬到 130,
`seat1` 重新「欠钱」,但因为走的是短码分支、没有重建队列,**它再也回不到队列里**。

`_advanceActor()`(`engine.js:406-413`)只看队列,队列里没有 `seat1`,于是本轮收口。

### 修复方向
`_rebuildPending` 不该只在「完整加注」时调用。
**任何抬高 `currentBet` 的动作都必须重建队列**,因为队列代表「谁还欠钱」。
`isFullRaise` 只应该决定「已行动玩家的 `hasActed` 要不要清零」(即是否重开加注权),
不该决定队列要不要重建。

### 复现
```
node tools/audit_closeround.mjs     # 最小复现(带 pending 队列轨迹)
```

## 四、🟡 Bug 3:短码全下后最小加注额漂高

### 规则约定
短码全下(增量不足一个完整加注)**不改变**「上一次完整加注额」,
所以下一个合法加注目标 = 上一个完整加注目标 + 上一次完整加注额。

### 实测
```
翻前加注到 100(增量 80,完整)  → minRaiseTo=180  lastFullRaise=80
seat4 短码全下到 120(增量 20) → minRaiseTo=200  ← 被抬高了

标准规则:下一个合法加注到 180 即可。
引擎行为:认为 180 太小,把它降级成「跟注 120」。
```

后续影响:如果没人做完整加注,这个被抬高的值会一直留在 `minRaiseTo` 上。
两轮短码全下会叠加:`101 → minRaiseTo=181`,`102 → minRaiseTo=182`。

### 根因
`engine.js:515`:

```js
st.minRaiseTo = Math.max(st.minRaiseTo, target + st.lastFullRaise);
//                                     ↑ 短码全下的目标额,不该用这个当基准
```

基准应该是「**上一个完整加注的目标额**」,而不是「短码全下的目标额」。

### 触发条件与频率
需要「先有一次完整加注,再来一次增量不足的全下」。
用 2760 手随机对局探测,**没有观察到「合法最小加注被错误降级」的实际案例** ——
因为加注者往往是本轮最后一个行动的人,轮不到他被这个值卡住。
所以这条**影响面窄,但逻辑确实与标准规则不符**。

### 复现
```
node tools/audit_minraise.mjs       # 4 项失败
```

## 五、🟡 Bug 4:平分底池时奇数余数给了按钮位

### 规则约定
`engine.js:753` 的注释写的是「余数按顺时针(**按钮左侧最近者优先**)分配」。

### 实测
```js
// engine.js:754
const ordered = [...winners].sort((a, b) =>
  ((a.seat - st.button + n) % n) - ((b.seat - st.button + n) % n));
```

这个距离函数给**按钮位自己**算出距离 `0`,给「按钮左侧第一家」算出 `1`。
所以排序结果永远是「按钮位排第一」:

```
按钮=0 → 排序 [0,1,2,3],首位 0(应为 1)
按钮=1 → 排序 [1,2,3,0],首位 1(应为 2)
按钮=2 → 排序 [2,3,0,1],首位 2(应为 3)
按钮=3 → 排序 [3,0,1,2],首位 3(应为 0)
```

**按钮位本人拿走了奇数余数**,而不是按钮左侧最近的赢家。
子代理的独立用例也复现了:按钮=0、赢家 0 与 2 时,座位 0 拿 17、座位 2 拿 16(应相反)。

### 影响
每个边池最多多/少 1 个筹码。金额小,但规则明确写错了。

### 复现
```
node tools/audit_oddchip.mjs
```

## 六、🟠 Bug 5:单挑时位置标签张冠李戴

### 实测
```
第 1 手: 按钮=seat0 小盲=seat0 大盲=seat1  标签={"0":"BTN/SB","1":"BB"}   ✓
第 2 手: 按钮=seat1 小盲=seat1 大盲=seat0  标签={"0":"BTN/SB","1":"BB"}   ✗
```

第 2 手按钮轮转到 seat1,但标签还是把 seat0 标成 `BTN/SB`、seat1 标成 `BB` —— **正好反了**。

### 根因
`engine.js:198-201`:

```js
if (inHand.length === 2) {
  map[inHand[0].seat] = 'BTN/SB';     // ← 按数组顺序,而不是按按钮位
  map[inHand[1].seat] = 'BB';
  return map;
}
```

`inHand` 是**按座位号**排列的数组,和按钮位无关。
按钮在 seat1 时,seat0 排在前,于是 seat0 被标成 `BTN/SB`。

### 影响
- 界面显示错位置(玩家看到的 D/SB 标记是错的)
- **AI 提示词里的位置也是错的**,会影响它的决策质量

### 复现
```
node tools/audit_betting2.mjs       # 场景 D
```

## 七、⚪ 两个隐患(不影响当前玩法)

1. **`seats` 没有上限校验**
   传 `seats > 9` 时,牌堆不够发,会静默发出 `undefined` 牌。
   界面滑杆限制在 2~9,所以正常玩法碰不到;但引擎层没有防御。

2. **`shuffle()` 未校验 `rand()` 的返回值**
   `cards.js:29`:`const j = Math.floor(rand() * (i + 1));`
   若 `rand()` 返回 `1.0`(越界),`j = i+1` 会读到 `undefined`,导致**丢一张牌**。
   当前的 `cryptoRandom()` 和 `Math.random()` 都不会返回 1.0,所以现实安全。

## 九、为什么现有测试跑过了却没抓到

| Bug | 现有测试为什么漏掉 |
|---|---|
| 短牌三条 > 顺子 | `selftest.mjs:72` 断言写错:它比较的是 `6s7d8c9hTs`(顺子)对 `JhJdJc2s2d`(**那是葫芦,不是三条**),实际测的是「葫芦 > 顺子」,所以永远通过 |
| 下注轮提前关闭 | 所有随机对局测试都不检查「本轮收口时是否还有人欠钱」这个不变量 |
| 最小加注漂高 | 测试只验「完整加注链」,没验「短码全下之后再有人加注」 |
| 奇数余数 | 测试只验「余数分完了吗」,没验「分给谁」 |
| 单挑位置标签 | 测试只验第 1 手,没验按钮轮转到另一方之后 |

**共性**:测试覆盖的是「正常路径」,缺的是**对抗性边界**——
短码全下、按钮轮转、奇数余数归属、不变量校验。

## 十、修复优先级建议

1. **Bug 1(短牌三条/顺子)** —— 一行改动(`SHORT_REMAP` 改成 `[0,1,2,4,3,6,5,7,8]`),
   同时修正 `CATEGORY_NAME_SHORT`;影响胜负和 AI 判断,优先修。

4. **Bug 4(奇数余数)** —— 距离函数改成从按钮左侧起算。
5. **Bug 5(单挑位置标签)** —— 按 `st.button` 判断谁是 BTN/SB。
